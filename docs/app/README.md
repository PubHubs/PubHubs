# Specific info for developing the App

## iOS Real-device testing: why `localhost` doesn't work.

A real device (unlike the iOS Simulator, which shares the Mac's network) can't reach `localhost` on the dev machine.
Android's `adb reverse` (see `mask run android ports`) tunnels the phone's own `localhost` back over USB, but iOS has no equivalent.

The fix:

### PHC / global-client and hub-client / Matrix API: LAN IP over plain HTTP

PHC already hands out hub/MSS URLs built from the `networkhost` alias, so `global-client`'s own `PUBHUBS_URL`/`PHC_URL` need to request that same IP, or the app never attempts the reachable address.
The same applies to `hub_client_url` (`pubhubs_hub/start_testhub.py`) and hub-client's `HUB_URL` (the Matrix/Synapse API). Plain HTTP is enough for all of these, and an HTTP parent embedding an HTTP iframe isn't restricted by the browser.

Note: hub-client's `PARENT_URL` deliberately does _not_ get this treatment, even though it's the same shape of "global-client's own URL" config as the others. `hub-client` runs as a single shared dev server across browser, Simulator, and real device (unlike global-client, which gets a separate LAN-IP-patched build just for iOS), so a single `PARENT_URL` value can't be right for both "browser opened at `http://localhost:8080`" and "real device needs the LAN IP" at once. It's left on its `localhost` default because `messagebox.ts`'s parent/child handshake — the thing that actually makes a hub usable in an iframe — doesn't need it to be correct on native: `NATIVE_SHELL_ORIGINS` already trusts the native shell's real origin (`capacitor://pubhubs-app.invalid`) regardless of `PARENT_URL`. (Setting `PARENT_URL` to the LAN IP via `VITE_PARENT_URL` was tried and reverted — it broke the handshake for ordinary browser dev, since a plain browser tab isn't a trusted native-shell origin and so needs an exact `PARENT_URL` match instead.) The one known gap this leaves: `pubhubs.ts`'s `centralLoginPage()` (SSO-login-completion redirect) and `RoomMessageBubble.vue`'s forwarded-message share link both build a URL from the literal `PARENT_URL` string, so those two specific flows may still target `localhost` unreachably on a real device — not fixed here.

- `ios/App/App/Info.plist` gets a matching ATS exception domain. It's gitignored and generated by `scripts/sync-networkhost-ip.js` from `Info.template.plist`. ATS exceptions are host-based, not port-based, so this one domain entry covers every plain-HTTP port on the `networkhost` IP — global-client's, hub-client's, and the Matrix API's alike.
- The tracked `global-client/public/client-config.js` keeps its `localhost` defaults, which is fine for web dev.
  For iOS, `scripts/patch-ios-client-config-ip.js` rewrites the _built_ `global-client/dist/client-config.js` to the LAN IP,
  after `npm run build:global:native` and before Capacitor copies `dist/` into the native project. `dist/` is gitignored and freshly rebuilt every time, the script only ever runs as part of the iOS build chain.
  `hub-client`'s own tracked `public/client-config.js` similarly keeps its `localhost` default for `HUB_URL`; for real-device testing, `maskfile.md`'s `hub client (n)` task overrides it via `VITE_HUB_URL`, which `client_config.ts`'s `adjustClientConfig()` reads at runtime. (`PARENT_URL` is deliberately left alone — see the note above.)
  For Android, `capacitor.config.ts` sets `androidScheme: 'https'`, so the app's own page origin is `https://pubhubs-app.invalid` — an https page fetching these plain-`http://` URLs would otherwise be blocked as mixed content.
  `MainActivity.java` allows mixed content in **debug builds only** (`WebSettings.MIXED_CONTENT_ALWAYS_ALLOW`, gated on `BuildConfig.DEBUG`), so release builds keep strict mixed-content blocking.

Both scripts read `pubhubs.toml` and run automatically via `npm run cap:sync:ios`, `cap:run:ios`, and `cap:open:ios`.

Note: hub-client does call `window.crypto.subtle` once, in `useRoomLibrary.ts`'s `makeHash()` — a SHA-256 file
hash for the optional, feature-flagged "Room Library" file-signing feature (`FeatureFlag.roomLibrary` in
`hub-client/src/stores/settings.ts`), not Matrix message encryption (real E2EE/olm/megolm isn't implemented
anywhere in this codebase — no room is ever created with `m.room.encryption`, and the matrix-js-sdk client is
never initialized with crypto support). `crypto.subtle` requires a secure context (`https://` or `localhost`),
which plain HTTP over a LAN IP isn't, but `makeHash()` already wraps it in a try/catch: if `crypto.subtle` is
unavailable, it logs an error and returns `''` instead of throwing, so the app doesn't need HTTPS for this to
work — the file-signing feature just silently no-ops.

### Yivi QR-login

The Yivi app itself, by default, refuses to fetch a QR-scanned session-pointer URL (`public_yivi_url`) over
plain HTTP (errors with `'https: remote server does not use https'`) — this is a hard requirement of the
upstream Yivi app, not something PubHubs added. Enable Yivi's "developer mode" on the phone that will scan
the QR code (see https://irma.app/docs/yivi-app/#developer-mode) — a one-time, per-device setting — and the
qr-code flow works over plain HTTP with no other infrastructure needed. See also
`docs/development/LOCAL_DEVELOPMENT.md`.

## Hub isolation

The app bundles hub-client (`npm run build:hub:native`, under `/hub/`) and serves it on a separate origin per hub, `<label>.hubs.pubhubs-app.invalid`, with the label derived from the hub ID. That keeps each hub away from the app shell (which holds the user's PubHubs login) and from the other hubs, as on the web. Android serves those hosts from `HubOriginWebViewClient`; iOS needs no serving code.

See [HUB_ISOLATION.md](HUB_ISOLATION.md) for the design, the extra checks, the Android verification and the known gaps (notably Capacitor's native bridge on iOS), and [IOS_ISOLATION_TEST.md](IOS_ISOLATION_TEST.md) for the iOS test plan.

## Release builds

Release builds talk to production, using the committed `global-client/config/client-config.production.js`. It's in the repository because F-Droid builds the app from our source.

- `npm run cap:sync:android:release` builds the clients with that config and syncs them into `android/`. It sets `PUBHUBS_RELEASE`, so `capacitor.config.ts` turns off cleartext traffic and ignores `capacitor.config.local.json`.
- Then, in `android/`:
  - `./gradlew bundleRelease` builds the app bundle for the Play Store, in `app/build/outputs/bundle/release/`;
  - `./gradlew assembleRelease` builds the APK, in `app/build/outputs/apk/release/`.
- **Signing:** set `PUBHUBS_KEYSTORE` (an absolute path), `PUBHUBS_KEYSTORE_PASSWORD`, `PUBHUBS_KEY_ALIAS` and `PUBHUBS_KEY_PASSWORD`. Without them the release build is unsigned, which is what F-Droid expects; it signs with its own key.
- **Version:** set `versionCode` and `versionName` in `android/app/build.gradle` on every release; F-Droid reads them from there.
  - `versionName` is the release version without the `v`, for example `3.6.0`.
  - `versionCode` is `MAJOR * 10000 + MINOR * 100 + PATCH`, for example `30600`. Play only accepts a version code once, and it has to go up.
  - Release candidates (`-rc0`) usually share the commit, and so the version code, with the final release. Only upload final releases to Play; share release candidates as an APK or through Play's internal app sharing, which doesn't need a new version code.
- **CI:** on a final release tag (`vX.Y.Z`), the `build-android` job builds the signed app bundle and APK and keeps them as job artifacts; upload the bundle to Play by hand.
  - It runs in the `android-build` image from `ilab/docker-build`, and fails when `versionName`/`versionCode` don't match the tag.
  - It signs with the upload key from the CI variables `PUBHUBS_KEYSTORE_BASE64` (the keystore, base64-encoded), `PUBHUBS_KEYSTORE_PASSWORD`, `PUBHUBS_KEY_ALIAS` and `PUBHUBS_KEY_PASSWORD`. They are protected, so release tags have to be protected too.
  - In merge requests and on main, `android-build-check` builds the app unsigned whenever something it depends on changed (`android/`, `capacitor.config.ts`, the npm package files, `global-client/config/`, the CI file), so a broken app build shows up before the release tag.

## Review mode

App store reviewers can't log in with a real Yivi identity, so the app has a hidden switch to a separate environment where they register with Yivi demo credentials.

- **Switching on:** tap the mascot on the login page ten times in quick succession, and confirm. The app clears the session and the hub list on this device, and reloads on the register page.
- **Switching off:** the "Review environment" label in the header of the login and register pages has a "Leave" button. Logging out doesn't leave review mode, because the app also logs out by itself, for example when a session expires.
- **Which environment:** `REVIEW_PHC_URL` in `global-client/config/client-config.production.js`; for now main (`https://phc-main.pubhubs.net`). While the `ph:review-mode` key is set in `localStorage`, that file sets `PHC_URL` to it before any module loads. Everything else (auths server, transcryptor, hubs) comes from that PHC.
- **Where:** only in the native app, and only with a `REVIEW_PHC_URL` configured, so not in development or on the web. The code is in `global-client/src/logic/reviewMode.ts`.
- The demo email address the reviewers use is effectively their password: anyone can issue themselves Yivi demo credentials with the same value. Keep it long and random, and only give it to the store.

## Future notes:

- **LiveKit (video calls) real-device support is unresolved, for a reason unrelated to HTTP/HTTPS.** `_video_call_web.py` hands the browser the same `LIVEKIT_URL` it uses server-side (see `docs/development/VIDEO_CALL_TROUBLESHOOTING.md`), which `start_testhub.py` sets to `http://localhost:{port}` — a real device can't reach the dev machine's `localhost` regardless of scheme, so real-device video calls were likely already broken before plain HTTP was reintroduced here, for the same "real device can't resolve localhost" reason described at the top of this doc.
- `Info.template.plist` sets `NSLocalNetworkUsageDescription`, so iOS 14+'s Local Network Privacy prompt shows up instead of silently blocking a real device connecting to the `networkhost` LAN IP.
- See also `docs/development/LOCAL_DEVELOPMENT.md` for the separate Apple Private Relay / Yivi Local Network permission pitfalls on real iOS devices.
