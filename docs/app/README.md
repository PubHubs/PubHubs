# Specific info for developing the App

## iOS Real-device testing: why `localhost` doesn't work.

A real device (unlike the iOS Simulator, which shares the Mac's network) can't reach `localhost` on the dev machine.
Android's `adb reverse` (see `mask run android ports`) tunnels the phone's own `localhost` back over USB, but iOS has no equivalent.

The fix:

### PHC / global-client and hub-client / Matrix API: LAN IP over plain HTTP

PHC already hands out hub/MSS URLs built from the `networkhost` alias, so `global-client`'s own `PUBHUBS_URL`/`PHC_URL` need to request that same IP, or the app never attempts the reachable address.
The same applies to `hub_client_url` (`pubhubs_hub/start_testhub.py`) and hub-client's `HUB_URL` (the Matrix/Synapse API). Plain HTTP is enough for all of these, and an HTTP parent embedding an HTTP iframe isn't restricted by the browser.

- `ios/App/App/Info.plist` gets a matching ATS exception domain. It's gitignored and generated by `scripts/sync-networkhost-ip.js` from `Info.template.plist`. ATS exceptions are host-based, not port-based, so this one domain entry covers every plain-HTTP port on the `networkhost` IP — global-client's, hub-client's, and the Matrix API's alike.
- The tracked `global-client/public/client-config.js` keeps its `localhost` defaults, which is fine for web dev.
  For iOS, `scripts/patch-ios-client-config-ip.js` rewrites the *built*  `global-client/dist/client-config.js` to the LAN IP,
  after `npm run build:global:native` and before Capacitor copies `dist/` into the native project. `dist/` is gitignored and freshly rebuilt every time, the script only ever runs as part of the iOS build chain.
  For Android, `capacitor.config.ts` sets `androidScheme: 'https'`, so the app's own page origin is `https://pubhubs-app.invalid` — an https page fetching these plain-`http://` URLs would otherwise be blocked as mixed content.
  `MainActivity.java` allows mixed content in **debug builds only** (`WebSettings.MIXED_CONTENT_ALWAYS_ALLOW`, gated on `BuildConfig.DEBUG`), so release builds keep strict mixed-content blocking. One known gap: hub icons/banners are loaded via a passive `<img>` tag, which Chromium auto-upgrades from `http:` to `https:` (same port) regardless of that WebView setting, so they may fail to load on Android in dev — cosmetic only, not fixed here (would need fetching them via `fetch()`+blob instead of `<img src>`).

Both scripts read `pubhubs.toml` and run automatically via `npm run cap:sync:ios`, `cap:run:ios`, and `cap:open:ios`.

Note: hub-client does call `window.crypto.subtle` once, in `useRoomLibrary.ts`'s `makeHash()` — a SHA-256 file
hash for the optional, feature-flagged "Room Library" file-signing feature (`FeatureFlag.roomLibrary` in
`hub-client/src/stores/settings.ts`), not Matrix message encryption (real E2EE/olm/megolm isn't implemented
anywhere in this codebase — no room is ever created with `m.room.encryption`, and the matrix-js-sdk client is
never initialized with crypto support). `crypto.subtle` requires a secure context (`https://` or `localhost`),
which plain HTTP over a LAN IP isn't, but `makeHash()` already wraps it in a try/catch: if `crypto.subtle` is
unavailable, it logs an error and returns `''` instead of throwing, so the app doesn't need HTTPS for this to
work — the file-signing feature just silently no-ops.

### Yivi QR-login

The Yivi app itself, by default, refuses to fetch a QR-scanned session-pointer URL (`public_yivi_url`) over
plain HTTP (errors with `'https: remote server does not use https'`) — this is a hard requirement of the
upstream Yivi app, not something PubHubs added. Enable Yivi's "developer mode" on the phone that will scan
the QR code (see https://irma.app/docs/yivi-app/#developer-mode) — a one-time, per-device setting — and the
qr-code flow works over plain HTTP with no other infrastructure needed. See also
`docs/development/LOCAL_DEVELOPMENT.md`.

## Future notes:

- **LiveKit (video calls) real-device support is unresolved, for a reason unrelated to HTTP/HTTPS.** `_video_call_web.py` hands the browser the same `LIVEKIT_URL` it uses server-side (see `docs/development/VIDEO_CALL_TROUBLESHOOTING.md`), which `start_testhub.py` sets to `http://localhost:{port}` — a real device can't reach the dev machine's `localhost` regardless of scheme, so real-device video calls were likely already broken before plain HTTP was reintroduced here, for the same "real device can't resolve localhost" reason described at the top of this doc.
- `ios/App/App/Info.plist` has no `NSLocalNetworkUsageDescription` key, so on an RFC1918 private LAN, iOS 14+'s Local Network Privacy prompt applies and could silently block a real device without it.
- See also `docs/development/LOCAL_DEVELOPMENT.md` for the separate Apple Private Relay / Yivi Local Network permission pitfalls on real iOS devices.
